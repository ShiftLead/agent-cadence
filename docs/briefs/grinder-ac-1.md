This is agent-cadence's part of the grinder brief (ShiftLead design §4.8, its TD-114): what this repo does differently from the template above and below it, and nothing the template already says. The team is **ac-grind**, started by `ao team start ac-grind` on the person's machine; your manager is **ac-manager**. Paul is not driving you.

**First reads, in place of the template's.** `CLAUDE.md`, then `files/docs/cadence.md` §1–§4 and §7 — there is no `docs/cadence.md` here, and no `docs/design.md`: the system's rules are `files/docs/cadence.md`, and a decision lives in `docs/plans/` or in its ledger entry (CLAUDE.md, *Decisions live in*).

**What this repo is.** agent-cadence is the **canonical source** of the cadence system that other repos run from a pinned commit (`agent-cadence`, cadence.md §9.19), and that shapes every fix:

- **The system lives under `files/**`**; the scripts you edit are in `files/scripts/`, not `scripts/` (which does not exist here). `docs/**` is this repo's *own* board, ledger and plans: `docs/ledger/` is the live ledger you work, `files/docs/technical_debt.md` the empty template that seeds consumers — never file an entry there. Same trap for `user_attention.md`.
- **The SYNCED FILE header does not bind you here.** The template says files carrying it are not yours to edit; that is a rule for *consumers*. Under `files/**` this repo holds the canonical copy the header points at, and editing it is the job.
- **A SYNC file change reaches every consumer on its next bump.** A convention change gets an entry in `files/docs/cadence-changes.md` (append-only, ≤3 lines, newest first); adding or removing a payload file edits both the array in `sync.sh` and the file-class table in `README.md` (`tests/test_readme_sync_table.sh` checks it); repo-specific behaviour stays out of SYNC files. Scripts stay **stdlib-only** Python 3 and bash.

**Where you work.** Your worktree is `.claude/worktrees/ac-grinder`; the main checkout is Paul's anchor — never touch it. After `git fetch origin` and `git status`, deal deliberately with anything a previous run left in the worktree before starting. The default branch is `main`; name work branches `tdNNN-<slug>`. A branch exists only to carry a PR, never as a save-point. **Memory is git-tracked in `docs/claude-memory/`** (TD-038, resolved 2026-09-25) — and **the memory path is per checkout** (TD-080, cadence.md §7.2): `hydrate_worktree.sh` writes your worktree its own `.claude/settings.local.json`, naming its own `docs/claude-memory`, so a memory note is a change on your branch and rides your PR; never commit one sitting uncommitted in a checkout that you did not write. Only a hydrated worktree carries the setting (the SessionStart hook says when the file is missing, is still the old symlink to the main checkout's, or names another checkout's memory — run the command it prints), so anything durable you learn still goes into the ledger entry you are working or `docs/plans/` first, never only into memory. Read `docs/user_attention.md` yourself rather than relying on the SessionStart report.

**The gate, in place of `pdm run test` / `pdm run lint`** — two commands, by hand, from the worktree root:

```
./run_tests.sh                               # the suite as one pass/fail — CI runs the same
for t in tests/*.sh; do bash "$t"; done     # by hand: each file prints its own "N passed, M failed"
ruff check files/scripts/
```

`bash tests/*.sh` runs ONLY the first file — the rest become its `$@`. Read every file's tally, not just the last; a `0 failed` after a `SKIP` line is a suite that skipped. The merge gate is `cadence/precheck` (TD-148, cadence.md §4.12): `python3 files/scripts/precheck.py --pr <n>` runs `docs/cadence.toml`'s `precheck` (those two commands, `CI=true`) in a clean worktree at the PR's head and records the status the cadence check's `ci` row requires — run it before the cadence check, on every head you merge. GitHub Actions (`.github/workflows/ci.yml`, TD-047) is not the gate: the account's minutes are a shared pool, and moving its trigger to `workflow_dispatch` is Paul's step — run the gate yourself first anyway. Tests stay **offline and fixture-driven**, override `HOME` and `XDG_CONFIG_HOME`, and **derive date fixtures from the run date** (TD-24). **Gate after the LAST change to the tree** — a review nit is an edit; so is a rebase.

**Review and merge.** The independent review is **Sonnet** (`/code-review`, or an Agent with `model: sonnet` — never your own model); doc-only PRs get the same fact-check. Brief the reviewer to **re-derive** the claim, not to read the diff; when you mutation-check a guard, self-chosen mutations share your blind spots — say so rather than claiming N/N killed. Record it as a PR comment whose first line is exactly `cadence-review: SHIP|FIXED|BLOCK · <model> · <code|docs> · <n> findings`. The cadence check is `python3 files/scripts/check_cadence.py --pr <n>` — the `/cadence` skill says `scripts/`, which is wrong in this repo. A merge here is `gh pr merge <n> --squash`, then `gh pr view <n> --json state` to confirm MERGED — **never `--delete-branch` from a worktree** (it merges, then fails on local cleanup, so a merged PR reads as failed). GitHub deletes the remote head; delete only your local branch. **Never commit to main**: the pre-push hook blocks it, and `ALLOW_MAIN_PUSH=1` is for cadence.md §4's carve-outs and never for you.

**The ledger's rules are cadence.md §2**, and `docs/ledger/` is written only through `files/scripts/ledger.py` (§2.12, TD-202: `new`, `set`, `note`, `edit`, `archive`, `reopen`, `renumber`; a hand edit goes through `ledger.py fmt TD-n`) — partial work stays live (§2.7), archiving (§2.8), numbering (§2.10: every id from `ao td next`, else `files/scripts/ledger_next_id.py` — never by hand).

**The lane: free-pick** from `docs/ledger/` as it stands on `origin/main`: pick from `python3 files/scripts/ledger.py --pickable`, which prints the pick order (the rank: highest **Priority** first, then id, unless the person has ranked the cards — cadence.md §2.4) and leaves out every entry with an open `**Blocked by:**` field (cadence.md §2, TD-064) — re-run before every pick; an entry filed an hour ago is as pickable as the rest. Each entry's Fix is a proposal; its **Why** is what you are resolving. **Never pick:**

- An entry the reader lists as **Blocked** — `decision (Paul)` marks Paul's calls (the reader's Blocked section names them; never a copy here), and an entry blocked on another waits until that one is archived. Promoting an entry is a ledger edit that removes its field (`ledger.py set TD-n --blocked-by ""`); no brief edit, no restart.
- Anything on `docs/user_attention.md` waiting for Paul, or whose Status says the decision is his but carries no field yet — then add `**Blocked by:** decision (Paul)` to it in your next PR.

An entry whose fix needs a decision only Paul can make (a convention with two defensible shapes), or would touch what the standing rules forbid, is dropped with the reason on the record.

**Standing rules** — these add to the template's never-list:

- **Never run `sync.sh` (its `--pin`) or `agent-cadence adopt` outside a test fixture.** Their last step appends the target to the machine roster `~/.config/agent-cadence/repos.txt` (append-only, cleaned by hand — a reviewer polluted it with `/tmp` paths on 2026-08-10). A hand run is only against a fixture under `$(mktemp -d)` with `AGENT_CADENCE_REG_DIR=$(mktemp -d)` set. Moving a consumer's pin (`agent-cadence bump`) is Paul's.
- **Never change this clone's git config.** the hook shims in the clone's shared hooks dir (TD-055) are the push guard for every worktree on this clone; a fix that wants it changed changes `install_git_hooks.sh` and says on the board what Paul runs.
- **Never touch another repo's checkout** (every other repo on this machine's roster, `~/shiftlead` among them), the roster, `consumers.txt`, GitHub repo settings (`gh api -X PATCH`, `adopt_repo_settings.sh --apply`), or `.github/` (CI is TD-047 and Paul's).
- **No edits to permission settings** or to `CLAUDE.md`'s rules. A `.claude/settings.json` change is a PR like any other, reviewed, and its permissions block is the seed's — nothing wider.

**Before you believe a number.** This system's recurring defect is a claim taken from a description rather than the thing — a Status line, a `~line` citation, a header comment that overclaims what a script does. Read a count off the command that produces it. State the scope inside any negative claim ("no hits **under `files/scripts/`**"), because a negative that closes work is never falsified by anyone. **Gates judge the index; detectors judge the disk** (cadence.md §7): before you add a check, decide which it is.
