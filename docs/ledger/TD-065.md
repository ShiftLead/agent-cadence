## TD-065: external trackers (Jira, Asana, GitHub Issues): decide whether the ledger and the attention board stay the one interface and trackers map into them, or trackers feed the tools directly

**Priority:** Low
**Type:** feature
**Added:** 2026-09-26 (Paul)
**Status:** **Decided 2026-09-26 (Paul): (a)** — the cadence records stay the one interface; trackers map into them, pull-only first, as a mirror process and never a SessionStart hook; one owner per field. Recorded in dev-cadence's private plan *2026-09-26-tracker-integration-one-interface*, which continues the 2026-08-26 board-store decision. **Remaining:** the per-tracker mapping table (in that doc) and the pull-only importer with fixture tests, for the first tracker a consumer actually needs. The `Blocked by` field (TD-064, landed 2026-09-26) is the relation the mapping is built on.
**Blocked by:** decision (Paul) — which consumer's tracker comes first; none needs one yet (2026-09-27). Sequence step 2 ran 2026-09-27: `sync-all.sh` from `b2217f3` opened a sync PR in each consumer (merging and grooming each ledger are those repos' sessions' work)
**Location:** `files/docs/cadence.md` §2 and §3 (the two record shapes); `files/scripts/nudge_user_attention.py` and `check_cadence.py` (today's readers); agentorc's shiftlead and team briefs (the other consumer of the same interface).

**Why:** the ledger (`TD-NNN`, Priority/Added/Status/Location/Why/Fix) and the attention board (dated items with an owner and a due date) are the interface the whole system reads — the hooks, the sweeps, the cadence check, the grinder and techlead briefs, and agentorc's shiftlead. Some consumer repos will have work tracked in Jira, Asana or GitHub Issues as well, and the question is which side is canonical. Two shapes: **(a) the cadence records stay the one interface** and each tracker maps into them — an issue becomes, or is mirrored as, a TD entry or a board item, with the tracker ID as a field, and every tool keeps reading one format (a TD/attention database replaces the markdown files if volume demands it, behind the same shape). **(b) trackers feed the tools directly** — each script grows an adapter that reads Jira/Asana/GitHub fields, and the markdown ledger is one source among several. The cost of (b) is that every reader, brief and rule acquires N field mappings, and the Why — the field that makes the ledger worth having, which no tracker has — is lost for tracker-born items. The cost of (a) is a sync problem: two copies of state, and the rule on which side a change is made must be explicit (the tracker is the source for status and assignee, the cadence record for Why and Fix, say). Left undecided, the first integration will pick a shape by accident.

**Fix:** a plan doc under `docs/plans/` (this repo's ADR form) recording the decision and, if (a): the mapping table per tracker (which tracker field feeds which cadence field, which side wins on conflict), the ID field an entry carries (`**Tracker:** JIRA-123`), and what a sync is — pull-only into the cadence records is the smallest shape that keeps one interface, with Blocked-by (TD-064) mapping one-to-one onto the tracker's blocked-by relation. The decision is made (see Status); what is left is the mapping table and the importer, in the order the plan doc's Sequence gives.
