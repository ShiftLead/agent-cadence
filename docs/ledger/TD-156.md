## TD-156: The `ci` row reads *unknown* for every session on a fine-grained GitHub token: a 403 on check-runs hides the `cadence/precheck` status it can read

**Priority:** medium
**Type:** debt
**Added:** 2026-10-26 (Paul, through Add entry; drafted by a consumer-b session)
**Status:** Built 2026-10-27 (this PR): GitHub's `check_runs()` turns a 403 on check-runs (not a rate limit; 404 and 422 unchanged) into `forge.ChecksForbidden`, a `ForgeUnreadable` carrying the commit statuses, so every other caller still reads it as unknown. `_row_ci()` judges on those statuses only when `precheck` is set, its status is on the head, and `head_workflows()` finds no workflow at the PR's head (read from its tree, so one the PR adds counts; a head the clone lacks is unknown) on `pull_request`, `pull_request_target` or a branch push (filtered or not) and none with unreadable triggers; its detail then says *judged on commit statuses*, and otherwise the row is unknown, naming why. §4.12 and `cadence-changes.md` say it; `tests/test_check_cadence.sh` (TD-156 block) covers each case with a stubbed `gh`. Open question answered conservatively: a GitHub App posting check runs with no workflow file is invisible from the clone, which §4.12 names. **Left:** the *Done when*'s live half — consumer-b's sessions on the fine-grained token, once Paul syncs consumer-b. **Still unknown in consumer-b after its sync (2026-10-27):** see *Amendment* below. **Amendment built 2026-10-27 (this PR):** `head_workflows(root, sha, default, head_branch)` skips a push trigger whose `branches` are all the literal default (no `branches-ignore`, `tags` or `tags-ignore`) when the PR's head branch is another, `origin/<default>` exists and the head is not its ancestor (the optional guard, taken); §4.12 and `cadence-changes.md` say it; `tests/test_check_cadence.sh` covers consumer-b's shape passing and each looser filter, a main head branch, a head on main and a missing `origin/main` reading unknown. **Left:** Paul syncs consumer-b; a consumer-b team PR's `ci` row then reads PASS.
**Waits:** event — Paul syncs consumer-b again (the *Amendment* is built); then a consumer-b team PR's `ci` row on the fine-grained token reads PASS, and this archives
**Location:** `files/scripts/forge.py` (GitHub `check_runs()`, ~line 418, which ends `return runs + self.statuses(sha)`); `files/scripts/check_cadence.py` (`row_ci()`, ~line 649); `files/docs/cadence.md` §4.12

**Why:** a fine-grained personal access token cannot be given a Checks permission: the token settings offer none (Paul looked, 2026-10-26; only GitHub Apps and classic tokens read check-runs). It can be given Commit statuses, read and write, which is all `precheck.py` and the `ci` row's real evidence need. But `check_runs()` reads `/commits/{sha}/check-runs` first, and its 403 makes the whole read `ForgeUnreadable`, so the `cadence/precheck` status the same token can read is never reached and the row is *unknown* (exit 3). consumer-b's team sessions hit this the evening of 2026-10-26: their token had Commit statuses added for consumer-b TD-059, `precheck.py` recorded `success` on every head, and `check_cadence.py` still exited 3 on each, so by the exit-0 rule no team PR merged itself. Eleven green PRs waited on the person until a session with a broader token merged them. The narrow token is the one sessions should hold, so the gate fails exactly the setup it should encourage. The workaround, a broader token, gives every session far more access than it needs.

**Fix:** (built; the *Amendment* below narrows its workflow rule) in GitHub's `check_runs()`, a 403 on check-runs (permission, not a missing commit: 404 and 422 keep reading as unreadable) still reads `statuses(sha)` and returns them, marked so the `ci` row (`_row_ci()`) can say *check runs unreadable (token lacks Checks)* in its detail. Open: whether that alone may pass. A repo where something does run on PRs must not merge past a red check run it cannot see. The `ci` row already detects that case (§4.12's ⚠ naming a tracked workflow that runs on every `pull_request` or push to the default branch), so the likely rule is: pass on the statuses when the repo sets `precheck` and has no such workflow; stay *unknown* otherwise. Tests in `tests/test_check_cadence.sh` with a stubbed `gh`: 403 plus a success status and no PR workflow passes; the same with a PR workflow reads unknown; 404 still reads unreadable.

**Amendment (2026-10-27; Paul chose to narrow the detector over changing consumer-b's workflow):** a consumer-b workflow runs on `push: branches: [main]` (path-filtered, plus `workflow_dispatch`). `head_workflows()` counts any push that is not tag-only, so under the 403 the `ci` row stays *unknown* on every consumer-b PR. A push filtered to only the default branch cannot post a check run on an open PR's head, which is a commit on the PR's own branch. This supersedes the Status's and §4.12's *a branch push (filtered or not)* for that one case:
- `head_workflows(root, sha)` gains the default branch and the PR's head branch (`pr["head"]`), passed from `_row_ci()`.
- A `push` trigger is exempt only when **all** of these hold:
  - it has `branches` and no `branches-ignore`;
  - every `branches` entry is a literal (no `*`, `?`, `[` or leading `!`) equal to the default branch;
  - it has no `tags` filter;
  - the PR's head branch is not the default branch;
  - the default branch is verified, meaning `origin/<default>` exists, as `check_base` guards it. `default_branch()` falls back to a bare `main`, and that fallback alone is not verification.
- Anything else still counts. `_hits()` is not the test: it asks whether the default matches, not whether only it does, so `['**']` would pass.
- Accepted blind spot: a head commit already on the default branch would carry the push's checks. Optionally guard it with `git merge-base --is-ancestor <sha> origin/<default>`.
- §4.12 and `cadence-changes.md` change in the same PR.
- Tests in `tests/test_check_cadence.sh`:
  - `branches: [main]` with a non-default head passes;
  - these stay unknown: head branch = default; unverified default; `branches: [main, 'release/*']`; `['**']`; `branches-ignore`; `branches: [main]` plus `tags`;
  - a tag-only push stays exempt, as now.

**Done when** a session on a fine-grained token holding Commit statuses (read and write) and no Checks runs `precheck.py --pr <n>` and then `check_cadence.py --pr <n>` on a consumer-b PR (whose repo keeps `build-ci-image.yml`'s default-branch push), and its `ci` row reads PASS (exit 0 where the other rows are green); in a repo with a workflow on `pull_request`, the same token still reads *unknown*; and the stub tests in **Fix** pass.
