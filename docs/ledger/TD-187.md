## TD-187: A repo's line endings are whatever its editors left: make text LF in every cadence repo, seeded by `.gitattributes`

**Priority:** medium
**Type:** debt
**Added:** 2026-10-28 (Paul, session `td-breakout`: "each of our repos should land on CRLF or LF (probably LF) … file it. We should consider a githook if its needed")
**Owner:** grinder
**Kind:** build
**Status:** Open
**Location:** `files/.gitattributes` (new SEED); `sync.sh` `SEED_FILES` and README's file-class table (`tests/test_readme_sync_table.sh`); `launcher/words.py` (`adopt` seeds it); `files/docs/cadence.md` (a rule, near §7's file conventions); `files/docs/cadence-changes.md`; possibly `files/scripts/git-hooks/` (a pre-commit check, only if `.gitattributes` proves not enough)

**Why:** nothing in the cadence says which line ending a repo uses, so each repo has whatever its editors produced. On 2026-10-28, `git ls-files --eol` showed:
- dev-cadence, ledgerboard, consumer-c, consumer-d and shiftlead have no CRLF.
- consumer-a has 281 CRLF files and 6 mixed ones. They are mostly in older docs and migrations, probably from `core.autocrlf` on a Windows clone.
- consumer-b has 192 CRLF and 2 mixed. Its `.gitattributes` pins only `*.sh` to LF.

The cost lands on every scripted edit. Python's default text-mode `open()` turns `\r\n` into `\n`, so a one-line edit to a CRLF file becomes a whole-file diff that collides with every in-flight branch touching it. That happened on a consumer-a PR: a 3-line change became a 136-line one, caught only by review. consumer-a built a mixing guard (its TD-408). It forbids *mixing* and counts an allowance down. But its docstring rules out bulk conversion: without a rule, a conversion is a collision paid file by file, forever. One repo-wide convention pays it once.

**Fix:**
1. **The rule:** a cadence repo's text files are LF. A file that must be CRLF says so in `.gitattributes` (`*.bat`, `*.cmd`, `*.ps1`, or a named fixture whose bytes matter). It goes in cadence.md, with a cadence-changes entry.
2. **The seed:** `files/.gitattributes` holds `* text=auto eol=lf` plus the CRLF exceptions above, and is added as a SEED. `adopt` writes it into a repo that has none. A `.gitattributes` rule overrides a clone's `core.autocrlf`, which removes the usual source. A repo that already has a `.gitattributes` (consumer-b) adds the line by hand.
3. **Existing repos:** the LF ones get the seed in a small PR each, which changes no bytes. The CRLF ones file their own backfill (consumer-a#TD-470, consumer-b#TD-096): each repo's team runs `git add --renormalize .` in one PR at a quiet moment and decides file by file whether any CRLF is needed. dev-cadence does not convert anyone's files.
4. **The hook:** consider a pre-commit check only if the attribute is not enough. Cases where it might not be: a file marked `-text` or detected as binary that holds text, or a repo whose `.gitattributes` lost the line. If one is built, it is a shipped hook (`files/scripts/git-hooks/`), installed by TD-055's shims. Decide after the backfills land and show whether CRLF still comes back.

**Done when** the seed and the rule ship, `adopt` writes the seed, every LF repo carries the line, and the two backfill entries exist in their repos.

**Related:** consumer-a#TD-470, consumer-b#TD-096 (the backfills); consumer-a's TD-408 (`tests/test_line_endings.py`, its mixing guard); TD-055 (hook shims).
