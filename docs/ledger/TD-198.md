## TD-198: `ledger.py new`: file an entry from flags, with its id taken from the counter

**Owner:** grinder
**Kind:** build
**Status:** Open
**Taken by:** b675de241e6c
**Blocked by:** TD-197
**Part of:** TD-173
**Location:** `files/scripts/ledger.py` (`new`); `files/scripts/ledger_next_id.py` (the take it calls); cadence.md §2.10 (numbering) and §2.12; ShiftLead's `ao td reserve` (TD-182), which `new` absorbs

**Why:** filing is the write agents do most, and where the header conventions slip most: field order, `Taken by` copied by hand from the take's output, a wait written as prose. With `new`, filing an entry is one command, and the file it writes is canonical by construction (TD-197's renderer).

**Fix:**
- `ledger.py new --title "…"` with a flag for every header field (`--priority`, `--type`, `--owner`, `--kind`, `--status`, `--blocked-by`, `--part-of`, `--location`, and `--field Name=value` for a repo's own fields). `--why`, `--fix` and `--done-when` each take a file, or `-` for stdin.
- The id comes from `ledger_next_id.py`'s take, and `new` writes the take's `by` as `Taken by` itself (hashed, TD-195). Once TD-188 lands it writes `Id take` in its place. `--id TD-n` files under an id already taken.
- It validates as TD-199's `set` does before writing: ids resolve, a decision comes last, a declared field's value is in its vocabulary. It refuses, writing nothing, and names the problem.
- It writes `docs/ledger/TD-NNN.md` (or appends to a v1 ledger) and prints the path. It commits nothing.
- Tests: an entry from flags passes `ledger.py --check` and `fmt --check`; a bad field is refused; stdin bodies work; two `new`s in a row take two ids.

**Done when** a session files a full entry with one `ledger.py new` command, and the file needs no hand edit to pass `--check` and `fmt --check`.

**Related:** TD-173, TD-182, TD-188, TD-195.
