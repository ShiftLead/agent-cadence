## TD-199: `ledger.py set`, `note` and `edit`: change an entry's fields, Status and sections without touching the file

**Priority:** medium
**Type:** feature
**Added:** 2026-10-29 (Paul, session `sl-tds`: "the TD-173 design is right, file the builds")
**Owner:** grinder
**Kind:** build
**Status:** Open
**Taken by:** b675de241e6c
**Blocked by:** TD-197
**Part of:** TD-173
**Location:** `files/scripts/ledger.py` (`set`, `note`, `edit`); `files/scripts/ledgerboard.py` (`parse_blocked()`, `parse_part_of()`, `declared()`: the checks it reuses); cadence.md §2.4, §2.12

**Why:** most entry edits after filing are one field (a `Blocked by` gaining an id, a Priority), a dated Status line, or a rewritten Fix. Done by hand, they are where TD-160's blocker ended up in a decision's pointer (TD-172) and where TD-151 and TD-154 waited in prose (TD-166). Checking each value as it is written stops those at the source, rather than in `--check` after the fact.

**Fix:**
- `ledger.py set TD-n --field value …` (the same flags as `new`). Each value is checked as it is written:
  - every id in a `Blocked by` or `Part of` resolves, here or in a roster repo;
  - `decision (<who>)` comes last, and its pointer holds no id;
  - a declared field's value is in its `Fields:` vocabulary;
  - an empty value removes the field.
- `ledger.py note TD-n "…"` adds a dated line to the Status (`YYYY-MM-DD: …`).
- `ledger.py edit TD-n --section why|fix|done --from <file|->` replaces one section's prose.
- Each refuses, writing nothing, and names the problem. Each writes through TD-197's renderer, so the result is canonical.
- Tests: one per check above; `note` keeps earlier Status text; `edit` leaves the header and the other sections byte-identical.

**Done when** every routine edit of an open entry's header, Status or sections is one of these three commands, and each refuses the slips TD-166 and TD-172 record.

**Related:** TD-173, TD-166, TD-172.
