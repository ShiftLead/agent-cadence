**Why:** §4.8 already describes more than one reviewer: "Iterated rounds with more than one reviewer model run one at a time, cheaper first", and doc-only PRs get "a fact-check against the repo". But the settings name one model, `review-model` (default `sonnet`). The second reviewer, and the order the rounds go in, live only in how a person and their sessions happen to work. In this repo that has meant Sonnet fact-checking against the code and Fable reviewing the design, run by hand and once started in parallel by mistake (2026-10-29, the TD-173 plan's reviews). A rule whose inputs aren't configured gets followed from memory.

The fact-check is a different job from a review round. It reads a diff and the files it cites, and checks each claim; it makes no judgement on design. ShiftLead's TD-857 is moving it to a Gemini CLI seat on a free tier, naming the reviewer `<adapter>/<model>`. So its model is chosen on different grounds than a design reviewer's, and may not be a Claude model at all.

**Fix (proposed; for the rounds):**
- **`review-model` takes an ordered list:** `review-model = "sonnet, fable"`.
  - The first model does the default single round (§4.8, TD-123's one round for a change that adds no mechanism). A one-value setting behaves exactly as today.
  - Iterated rounds go down the list in order. That is §4.8's "cheaper first, one at a time", now in configuration.
  - A list may repeat a model, for alternating rounds (`"sonnet, fable, sonnet"`).
  - `cadence_config.py get review-model` prints the list as written, and `get review-model --first` (or a sibling key reader) prints the round-one model, so a reader that wants one model still gets one.
- **`fact-check-model`:** the model, or `<adapter>/<model>`, for a doc-only PR's fact-check (§4.8) and for any fact-check round of an iterated review. Unset, it falls back to `review-model`'s first item, so no repo changes behaviour.
- **§4.8 says which job each key does,** and that a fact-check round goes before the design rounds when a change has both, since a design review should read checked facts.
- **The evidence line is unchanged:** `cadence-review: … · <reviewer model> · …` already names whichever model ran (§4.9).
- **ShiftLead:** its techlead review and TD-857's fact-checker seat read these keys. Filed there as a shiftlead entry once the shape is agreed.
- **Tests:**
  - a list parses, and `--first` reads its head;
  - a single value is unchanged;
  - `fact-check-model` falls back to the first `review-model`;
  - the env override (`CADENCE_REVIEW_MODEL`) takes a list too;
  - a malformed list is an error naming the key.

**Done when** a repo can name its reviewers in order and its fact-checker separately in `docs/cadence.toml`, §4.8 and §9.18 say what each key does, the procedure asks for each round from them, and a `cadence-changes.md` entry announces it.
