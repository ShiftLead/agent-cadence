## TD-207: `precheck.py --pr` on a fork's PR runs the fork's code on the machine, with the person's credentials

**Priority:** medium
**Type:** debt
**Added:** 2026-10-30 (Paul, session `td-191`: "We should probably record TDs in agent-cadence and shiftlead for this as well")
**Owner:** grinder
**Kind:** build
**Status:** Open. The shape is agreed (Paul, 2026-10-30): a refusal with a deliberate override, and a §4.12 line for public repos. The flag's name and the refusal's wording are still to be agreed.
**Taken by:** ao-agent-cadence-td-191
**Blocked by:** decision (Paul)
**Location:** `files/scripts/precheck.py` (its `--pr` path fetches the forge's head ref, "a fork's head included"); `files/docs/cadence.md` §4.12; `files/scripts/check_cadence.py` `gating_events` / `head_workflows`; `files/docs/cadence-changes.md`; `tests/test_precheck.sh`

**Why:** the precheck is the merge gate in every repo that sets `precheck` in `docs/cadence.toml`. It checks out the PR's head in a clean worktree and runs the repo's own commands there, such as `./run_tests.sh` and the lint. On a PR from a fork, those commands are the fork's. A stranger's code then runs on the person's machine, with their `gh` token, their SSH keys and their home directory in reach. The clean worktree is no sandbox.

Nothing stops it today. ShiftLead's sync pass declines a fork before it prechecks (`sync.py` `decline()`), but a session or person running `precheck.py --pr <n>` by hand gets no warning. A public repo is where this starts to happen. agent-cadence decided its own case in TD-192: forge CI runs on fork PRs, and Paul reads the diff first. That rule lives only in this repo's CLAUDE.md, so it reaches no consumer.

**Fix:**
1. `precheck.py --pr` reads whether the head is a fork's. `forge.py` already reports it for both forges as a PR's `cross_repo` (GitHub's `isCrossRepository`, GitLab's `source_project_id` against `target_project_id`; TD-186). On a fork's head it refuses, exit 2 ("nothing ran"), before anything is checked out. The refusal names the PR and says what to do first: read the diff, and see the forge's CI green.
2. A deliberate override, an explicit flag (the name is to be agreed, e.g. `--fork-ok`), runs it. The recorded status's description says so.
3. cadence.md §4.12 gains a line for a public repo: forge CI runs on a fork's PR (adapt per repo, e.g. a job `if:` on the head repo), and a fork's precheck is the person's, never a session's. A `cadence-changes.md` entry tells consumers.
4. The detectors read the fork-only form. `check_cadence.py`'s `gating_events` and `head_workflows` count a `pull_request` trigger whose every job's `if:` requires a head repo other than the base as fork-only, not as gating every PR. That fork-only form is what §4.12's new line names. Then agent-cadence's own `ci.yml` (TD-192) stops drawing the ⚠ *runs on every pull_request* on every PR.
5. Tests: a fixture PR whose head repo differs is refused with exit 2 and nothing checked out; with the flag it runs; a same-repo PR is unchanged. The detectors pass a fork-only workflow and still warn on a plain `pull_request` one. `forge.py` reports `cross_repo` only when asked (`forge.py` ~372), so the precheck's read asks for it.

**Ask:** what is the override flag called, and does the refusal stand for every fork's PR, or only in a public repo?

**Done when** `precheck.py --pr` on a fork's PR refuses without the flag, cadence.md says how a public repo gates a fork's PR, and the suite covers both paths.
