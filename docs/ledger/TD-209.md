## TD-209: Test date fixtures are 24-hour arithmetic, so the suite fails in the hour before a DST change

**Priority:** low
**Type:** debt
**Added:** 2026-10-31
**Owner:** grinder
**Kind:** build
**Status:** Open
**Taken by:** ao-agent-cadence-ac-grinder
**Location:** tests/test_p2_report.sh (the +2d Swept checks, ~283), every tests/*.sh with `date -d '<n> days'`

**Why:** GNU `date -d 'N days'` adds N×24 hours, not N calendar days. Across a DST change that lands an hour short. On 2026-10-31 at 00:06 MDT, `date -d '2 days' +%F` printed 2026-11-01, because the clocks fall back on Nov 1. `test_p2_report.sh`'s "+2d stamp read as fresh" and "+2d deep stamp read as fresh" then failed on main and on every PR. This happens from 00:00 to 01:00 on the night before a fall-back, and the same thing hits a `N days ago` fixture after a spring-forward. In that window the suite, and so every `cadence/precheck`, is red for a reason that says nothing about the code. TD-24 already moved the fixtures to the run date, and this is the hole that is left.

**Fix:** Compute the dates DST-safe. One way is to anchor at noon: `date -d "$(date +%F) 12:00 +N days" +%F`, and the same for `ago`. Another is to export `TZ=UTC` at the top of each test that does date arithmetic, so that `date` and Python's `date.today()` agree and no DST applies. Do it in every `tests/*.sh` that uses `date -d '<n> days…'` (grep `date -d '[0-9]`). A check pins the form: it computes the chosen expression under `TZ=America/Denver` from a fixed base of 2026-10-31 00:30 (no faketime needed: `date -d "2026-10-31 00:30 ..."`) and expects 2026-11-02.

**Done when:** every `tests/*.sh` date fixture is calendar-day arithmetic, and the suite passes run inside a DST change's hour.
