**Location:** files/docs/cadence.md §4.8 (*The end-of-rounds item*); files/scripts/board_edit.py (`passthrough()`, add); files/scripts/ledgerboard/board.py (vendored; v2.4's add); files/docs/cadence-changes.md; tests/

**Why:** A design's end-of-rounds item holds its builds (the person's layer §2.4; cadence.md §4.8 *The end-of-rounds item*), but §4.8 does not say how the item names them, and `board_edit.py add` cannot write the field that would. Under ledgerboard v2.4 that gap has two costs:

- **The sweep re-asks for each held build.** v2.4's `covers()` (ShiftLead/ledgerboard `SPEC.md`, the sweep's functions; target design §3.2) counts a build's `decision (<person>)` gate as covered only by a `decide` item whose Context names that build and the gate, or names its parent (the build's `Part of`) with the gate and the build among the item's `Parts:`. An item written `Context: TD-<plan>.` alone covers no build, so v2.4's sweep files one `Go | Not yet` item per held build beside the end-of-rounds item: the same question asked again, once per build.
- **A consumer cannot list what the item holds.** shiftlead's Queue (shiftlead TD-1378, TD-1380) reads the item's `Parts:` to show the builds a Go releases; without it, it has nothing to show.

`Parts:` is v2.3's field (SPEC *Board*, `Parts:`; agent-cadence already vendors v2.3, so every reader here reads it), but SPEC leaves its writer to v2.4, and the vendored `board.py add` takes no parts flag. Asked for by shiftlead's TD-1378 design (ShiftLead/shiftlead PR #2911); shiftlead's TD-1381 brings the wording into its designer brief after its pin bump.

**Fix:** 1. **cadence.md §4.8**, *The end-of-rounds item*: the item is written `Context: TD-<plan> decision (<person>). Parts: <each held build>.`, its builds each `Part of` the plan entry, so `covers()` reads every held build as covered by the one item. Say what a build filed after the item does (not among its `Parts:`; it needs its own item or a new snapshot, target design §6's parent snapshot). This is a convention change: add a `files/docs/cadence-changes.md` entry (§3), and the layer wording follows with TD-220.
2. **`board_edit.py add`** writes the line's `Parts:`: if v2.4's `board.py add` takes the parts (an `item_line(parts=)` flag), the passthrough carries it with no code here (`passthrough()` takes `LBB.TAKES["add"]`); if it does not, file the flag as a ledgerboard entry rather than writing the field here, since the format and its writers are ledgerboard's (TD-213).
3. A test: `board_edit.py add --kind decide … --parts TD-a,TD-b` writes `Parts: TD-a, TD-b.` after the Context, and the vendored `covers()` reads both builds as covered.

Check against TD-220 (cadence.md follows v2.4) before building: step 1 may land as part of it.

**Done when:** cadence.md §4.8 names the end-of-rounds item's gate and `Parts:`, `board_edit.py add` writes `Parts:`, a test shows v2.4's `covers()` reading each held build as covered, and cadence-changes.md records it.
