## TD-222: ledgerboard v2.4's check() raises on a field below an entry's header block: ledger.py guards it until a release flags it again

**Priority:** Low
**Type:** debt
**Added:** 2026-11-04
**Status:** Open
**Taken by:** ao-agent-cadence-ac-grinder
**Location:** files/scripts/ledger.py check()

**Why:** ledgerboard v2.4's `check()` raises `Refused` on an entry with a field below its header block — its Log reader (`reassigns()` → `log_lines()` → `_entry_parts()`) refuses the entry where v2.3's check flagged it ℹ and read it anyway — so one such entry stops the check for the whole ledger. TD-215 vendored v2.4 with a guard in `ledger.py`'s `check()` wrapper that turns the `Refused` into one error naming the entries (kind `check-refused`), so `--check` and the cadence check's `ledger` row say what is wrong instead of a traceback. The guard is a second reading of the package's internals (`_entry_texts`, `log_lines`) and should go once ledgerboard fixes it upstream (reported to ledgerboard's techlead 2026-11-04, mail m-926bd41cbb05).

**Fix:** When a ledgerboard release flags the entry again instead of raising, vendor it and remove the guard from `ledger.py`: `guarded_check()` and the `LBL.check = guarded_check` binding the package writer gates through (TD-216), `_log_refused`, and the re-run without the refused entries that keeps each one standing ℹ when unchanged since `--since`; with the `check-refused` assertions in `tests/test_ledger.sh` and the below-block case in `tests/test_ledger_edit.sh`.

**Done when:** `ledger.py check()` calls `LB.check()` with no guard, and `tests/test_ledger.sh`'s below-block fixture is flagged by the package itself.
