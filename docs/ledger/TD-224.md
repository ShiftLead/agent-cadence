## TD-224: A merged tool PR is taken as one commit from its tip's subject: a rebase-merged PR passes a carve-out on its last commit alone

**Priority:** Low
**Type:** debt
**Added:** 2026-11-05
**Status:** Open
**Id take:** 6c356e6e124a4556851c0b1cc69c4176
**Location:** files/scripts/check_cadence.py (_tool_pr_commit); files/scripts/forge.py

**Why:** The review row's tool carve-outs (`row_board_edit_pr`, `row_queue_edit_pr`, and since TD-218 `row_lift_pr`) let a PR merge with no review comment when it is one commit. `_tool_pr_commit` infers that for a **merged** PR from its merge commit alone: one parent, and a subject ending `(#n)`. A rebase merge of a multi-commit PR also leaves a one-parent tip, and the last commit's subject is whatever its author typed. The carve-out then reads only `merge_sha^..merge_sha`, and an earlier commit's edits go unseen. A lift could, for example, be computed on top of a base the first commit polluted, and `decide_lift`'s byte-equality would carry that pollution through. An open PR is safe, because its count is `rev-list default..head`. This repo is squash-only, so it cannot reach here today; a consumer that allows rebase merges can. Found by the Sonnet review of PR #101.

**Fix:** For a merged PR, establish the one-commit property from the forge, not the subject: the PR's commit count (GitHub `commits` in `gh pr view --json`, GitLab's MR commits), added to forge.py's PR record and read by `_tool_pr_commit`. With no count, the carve-out does not apply.

**Done when:** A rebase-merged two-commit PR whose last commit carries a `(#n)` subject fails each tool carve-out, with a fixture per backend.
