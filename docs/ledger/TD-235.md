## TD-235: The commit hook reads a multibyte `core.commentChar` comment line as content, so a comments-only message gets trailers and commits

**Priority:** Low
**Type:** debt
**Added:** 2026-11-05
**Owner:** grinder
**Kind:** build
**Status:** Open
**Id take:** af28b7d8986e47e8acc98c046cebcf1a
**Location:** files/scripts/git-hooks/prepare-commit-msg (the awk comments-only test); tests/test_prepare_commit_msg.sh

**Why:** git (2.45+) accepts a multibyte `core.commentChar`, such as `§`. The commit hook reads it into `cc`, where `${#cc}` counts characters under a UTF-8 locale, so it keeps `§`. But its comments-only test is `awk`'s `substr($0, 1, 1) != c`, and on this machine's awk (mawk) that compares one byte with the two bytes of `§`. Every comment line then reads as content, so a message with nothing but comments gets the co-author and `Agent-Model:` trailers, and the commit git was about to abort as empty goes through as a commit of only trailers. That is the case the test exists to stop (cadence.md §9.9). Found while writing TD-232's parity test: a `printf '§ only\n'` message with `core.commentChar=§` and `LANG=C.UTF-8` gets both trailers from the hook on origin/main at cf95667 as well, so TD-232 did not cause it.

**Fix:** Compare the comment char as a prefix of the whole line rather than as its first character: `index($0, c) == 1` (byte-safe in every awk), or pass the length in and use `substr($0, 1, n)`. The scissors-line test already compares the whole line. Add a `tests/test_prepare_commit_msg.sh` case with `core.commentChar=§` under a UTF-8 locale, skipped where git refuses a multibyte comment char.

**Done when:** A comments-only message under a multibyte `core.commentChar` is left untouched by the hook, as the `#` case is, and a test case holds it.
