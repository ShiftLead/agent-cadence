## TD-248: Two PRs that each add a board item always conflict: board_edit.py add inserts at the top of the section, GitHub's merge runs no merge driver, and each conflict is a hand rebase and a re-precheck

**Priority:** medium
**Type:** debt
**Added:** 2026-11-07 (ShiftLead's designer ao-shiftlead-designer-ao-1, through ao td add for ShiftLead TD-1482; drafted by ao-agent-cadence-ac-techlead)
**Status:** Open
**Id take:** c4bcfda7052c475ca1e763529cb0113a
**Location:** files/scripts/board_edit.py (add, and a new replay); files/scripts/check_cadence.py row_board() ~2161 (reads a PR's board writes from the net diff); files/scripts/ledgerboard/board.py _under() ~220–235 and plan_add() ~273–329 (vendored from ShiftLead/ledgerboard); files/docs/cadence.md §3.4 (take both sides; the board row), §3.5 (add)

**Why:** Two PRs that each add a board item conflict every time, and each conflict costs a hand rebase and a full re-precheck. `board_edit.py add` hands the write to ledgerboard's `plan_add()`, which inserts the new item above the first item of its section (`_under()`, `files/scripts/ledgerboard/board.py` ~220–235). So two concurrent adds always write the same line. GitHub's merge does not run the merge drivers named in `.gitattributes`, so the conflict cannot be settled there and someone has to rebase by hand. Each rebase moves the head, so the precheck runs again (TD-245 reuses a pass only on an identical tree, and a rebase onto a moved main does not give one).

ShiftLead counted more than six such rebases (its PR #3025 was rebased three times). It asked for this entry from its TD-1482 (ShiftLead's designer, 2026-11-07), which waits on it and names this id. Every consumer that runs `board_edit.py` from its pin pays the same cost.

cadence.md §3.4 already says what the resolution is: *a board conflict is resolved by taking both sides, unread*. But no tool does it. A session rebases, edits the conflict markers by hand, and has to get a result the `board` row will pass, which means one the writers could have written.

**Fix:** Three shapes, which can be done separately:

1. **`board_edit.py replay`** (this repo, the wrapper). Take the base branch's board and archive, read the branch's own board writes from the **net change of the board and `docs/user_attention_archive.md` between the merge base and the branch's head**, and apply each write again onto the base board through the same `plan_*` calls. The writes are read from the diff, not from commit subjects: a session runs `board_edit.py` with `--no-commit` and the write rides its PR's ordinary commit (§3.5), so most board writes carry no helper subject (ShiftLead's designer, 2026-11-07, for its TD-1482). The cadence check's `board` row already reads a PR's board writes this way (`row_board()` → ledgerboard's `board_change_problems()`, files/scripts/check_cadence.py ~2161, over the merge base and the head), so replay classifies each item line's net change the same way: a new item is an add, and a changed one is a snooze, due, decide, reply or done of its base line. An item that left the board for the archive is a `done` that reached `ARCHIVE_AT` (§3.4): it is not replayed as a move. Its `done` is replayed, and the archive runs again on the result, writing the archive file from the base's copy, if the threshold is still met. An edit addressed by line finds its item by its head text, not its old line number. A write that no longer applies (the item is gone, or was already closed on the base) is refused by name rather than guessed. This is §3.4's *take both sides* as one command, and the result is what the helpers would have written, so the `board` row passes it. It removes the hand edit. It does not remove the re-precheck, because the head still moves.
2. **An insertion point two adds rarely share** (for example, ordered by Due, then key). Only this one avoids the conflict, and with it the re-precheck. It is ledgerboard's `plan_add()`/`_under()`, so it is an upstream change to ShiftLead/ledgerboard, vendored back by `vendor_ledgerboard.sh`, not an edit here. It also changes the order the person reads the board in, so it is a layout decision, not only a fix.
3. A `merge=union` driver for the board in the seed's `.gitattributes`. This would make a local rebase take both sides by itself. GitHub ignores it, so the rebase is still by hand, and union duplicates an item that both sides edited (§3.4's *appear twice*). Recorded so it is not proposed again as the cure.

Recommended: (1) here. It is additive and settles every kind of board conflict, not only add/add. If the re-precheck cost still matters after it lands, (2) goes to ledgerboard's ledger as its own entry.

**Done when:** `board_edit.py replay` re-applies a branch's own board writes onto the base branch's board and commits the result. A test covers two branches that each add an item under the same section, and an add plus a done on the same item, both settled by replay with no hand edit. The command is named in cadence.md where the board helpers are, with a `files/docs/cadence-changes.md` line.
