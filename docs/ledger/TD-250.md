## TD-250: In a pinned repo cadence_changes.py reads no changes: a bump's convention changes reach no starting or running session

**Priority:** medium
**Type:** debt
**Added:** 2026-11-07 (Paul, through his session ao-led-tds-ledger; drafted by ao-agent-cadence-ac-techlead)
**Status:** Open
**Id take:** 964fac7de348493c9c835ca67569e028
**Location:** files/scripts/cadence_changes.py changes_path() ~111, origin_entries() ~122; launcher/words.py (_source_clone, ensure_tree); files/docs/cadence.md §3.7 (2), §9.19, §7.9; files/docs/cadence-changes.md; ShiftLead docs/ledger/archive/TD-1025.md (dev-cadence's entry, the drafted design)

**Why:** In a repo that runs agent-cadence from a pin (cadence.md §9.19), `cadence_changes.py` reads no convention changes. So a bump's changes reach neither a session starting in it (`--hook`, the SessionStart hook of §3.7 (2)) nor a session already running (`--json`, which ShiftLead's home relays, §3.7 (3)). The only one who hears of a change is the reviewer of the bump PR, through its body. §3.7 makes `docs/cadence-changes.md` the way a convention change reaches sessions, and for every pinned consumer that way is silent.

The cause: `changes_path()` (`files/scripts/cadence_changes.py` ~111) returns the path beside the script only when the script lives inside the repo. Run from the pinned tree (the launcher's cache, outside the repo), it falls back to the consumer layout, `docs/cadence-changes.md`. A migrated repo has no such file, because `sync.sh --pin` removes the SYNC copies and `docs/cadence-changes.md` is one of them (`sync.sh` `SYNC_FILES`). So `origin_entries()` (~122) reads `origin/<default>:docs/cadence-changes.md`, gets nothing, and both modes say nothing, with no error.

Verified 2026-11-07 by the asker on agent-cadence main (`changes_path` / `origin_entries`), and in a pinned ledgerboard worktree, where `--list` prints *no cadence changes*. Checked again in the code while filing.

Asked by Paul on 2026-11-07, through his session `ao-led-tds-ledger`. It was drafted for him on 2026-10-26 as ShiftLead's TD-1025 *dev-cadence's entry*, and never filed, because dev-cadence had no question seat then.

**Fix:** Where the repo's `docs/cadence.toml` on `origin/<default>` holds an `[agent-cadence]` pin, read `files/docs/cadence-changes.md` at the commit that pin names, from the launcher's clone of the source, never from the repo. A repo with no pin on origin, this repo among them, reads as today.

Start from the drafted design: ShiftLead's archived `docs/ledger/archive/TD-1025.md`, section *dev-cadence's entry*, and its design §6 rule 12 *In a pinned repo*. It covers:
- `--json`: the landed walk (each heading's `landed` is the merge on origin whose pin brought it in, and a rollback then a rebump lands it again).
- `--hook`: the bump rule (an entry a bump brought prints once per worktree, the first of two bumps within `RECENT_DAYS` included).
- The *behind* line, comparing the worktree's pin with origin's.
- Its bounds: the cache lock taken only to clone or fetch, non-blocking with a deadline, exit 2 on a miss, and no source fetch from `--hook`.

Rename dev-cadence to agent-cadence throughout (the `[agent-cadence]` table, `agent-cadence path`). Check each of its claims about the launcher (`launcher/words.py` `_source_clone`, `ensure_tree`, the cache layout and locks) against the code as it is now. The draft predates the rename and the launcher's later changes.

This changes what consumers run (cadence.md §3.7 (2), §9.19, and §7.9's pin-reader row, a new reader of `origin/<default>:docs/cadence.toml`). So it needs a `files/docs/cadence-changes.md` line, and the plan's class is wide under §4.8 if it goes through design rounds.

**Done when:** In a pinned repo, `--json` and `--list` give the entries of origin's pin, with `landed` at the merge that brought each, and `--hook` prints an entry a bump brought, once per worktree. A synced copy and this repo keep their reading. cadence.md §3.7 (2), §9.19 and §7.9 say so, and offline fixture tests hold each case.
