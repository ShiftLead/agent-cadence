## TD-252: agent_sessions.py has no Grok Build backend, so a Grok session in a worktree is unseen by the anchor guard, the reaper's idle gate and the session index

**Priority:** medium
**Type:** debt
**Added:** 2026-11-11 (ShiftLead's designer ao-shiftlead-designer-ao-1, through ao td add for ShiftLead TD-1550/TD-1637; drafted by ao-agent-cadence-ac-techlead)
**Status:** Open

**Blocked by:** event (grok-adapter-built)
**Location:** files/scripts/agent_sessions.py (BACKENDS ~37, the per-tool branches ~113–235, beside the gemini and codex backends); files/scripts/cadence_config.py (the agents key ~73); files/docs/cadence.md §9.18 (agents); tests/test_agent_sessions.sh

**Why:** A session of xAI's Grok Build CLI in a worktree is invisible to the safety nets. `agent_sessions.py` is the one module the nets ask about agent sessions (TD-100): the anchor guard (`check_anchor.py`), the reaper's idle gate (`reap_worktrees.sh`), the session index (`list_sessions.py`) and the sweep row (`nudge_user_attention.py`). Its `BACKENDS` is `("claude", "codex", "gemini")`, so a live Grok session reads as *nobody here*. The anchor guard would let a second agent into that directory, and the reaper's idle gate could judge the worktree idle and report it reapable under a live session. Naming `grok` in the `agents` setting (cadence.md §9.18) would at least read as *cannot see* (no backend), not as nobody, but nothing tells a repo to do that.

ShiftLead's TD-1550 is designing a Grok adapter (its TD-1637). Once that is built, ShiftLead's own sessions can be Grok sessions in this cadence's worktrees, so the gap becomes real then. ShiftLead's designer asked for this entry (ao-shiftlead-designer-ao-1, 2026-11-11).

What the asker reported about Grok's state, not yet checked against a real install: a profile's sessions live under `GROK_HOME` (default `~/.grok`), in a `sessions/` tree with one directory per session id.

**Event (grok-adapter-built):** ShiftLead's Grok Build adapter (its TD-1637, from the TD-1550 design) is built and its entry archived. Only then can a Grok session run in a cadence worktree, and only then is there a real install to read the layout from.
check: file-contains ShiftLead/shiftlead docs/ledger/archive/TD-1637.md "TD-1637"

**Fix:** Add a `grok` backend beside `codex` and `gemini`, built the same way: read the session directories under `${GROK_HOME:-~/.grok}/sessions/`, find a session's directory by the cwd it records, and take liveness from `/proc`, as Gemini's (dev-cadence TD-109) and Codex's (dev-cadence TD-102) backends do. Codex's is the nearer model, since it also has a home override (`CODEX_HOME`) and a `sessions/` tree. Add a `grok_format_note()` canary, like the others, so that a change in Grok's layout reads as *cannot see* and not as *nobody*. Add a resume hint only if the CLI has a resume flag. Also add `grok` to the `agents` key's text in cadence.md §9.18 and `cadence_config.py`, and a `cadence-changes.md` entry.

First check the layout against a real Grok Build install: where the cwd is recorded, what the process's comm and argv look like, and which file it holds open. Without that, the backend would be built from a description.

**Done when:** `agent_sessions.py` lists a live Grok Build session in a worktree from a fixture `GROK_HOME` with a faked `/proc` entry, reports `grok` as *cannot see* when `GROK_HOME` is unreadable, and has a case in `tests/test_agent_sessions.sh` for each.
