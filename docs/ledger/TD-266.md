## TD-266: The remote tier cannot read a GitLab repo's v3 board: forge.py's GitLab class lists no directory

**Priority:** low
**Type:** debt
**Added:** 2026-11-14
**Status:** Open
**Id take:** 6ac6b4bcd1cd4e44a6eaa504455511ee

**Why:** `/attention remote` reads a repo it has no clone of through the forge (`nudge_user_attention.py`'s `_remote_board()`). Since ledgerboard v3.0 (TD-263) a board is a directory, and `docs/user_attention.md` is only a stub naming it, so the remote tier must list the directory to read any item. `_remote_board()` lists it through GitHub's contents API, where a read of a directory returns its JSON listing; `forge.py`'s GitLab class has `read_file()` alone (`files/scripts/forge.py`, its `read_file` near :1273) and no tree listing. So a GitLab-hosted repo with a v3 board shows *not read: stub* in the remote tier, and its open items never reach `/attention remote`.

**Location:** files/scripts/forge.py; files/scripts/nudge_user_attention.py (_remote_board); tests/test_remote_tier_gitlab.sh

**Fix:** Give `forge.py`'s forge classes one directory-listing call (GitHub: the contents API's listing; GitLab: `GET /projects/:id/repository/tree?path=…&ref=…`), and have `_remote_board()` call it rather than relying on a directory read through `read_file()`. Cover it in `tests/test_remote_tier_gitlab.sh` with a v3 board fixture.

**Done when:** `tests/test_remote_tier_gitlab.sh` reads a v3 board's open items through the GitLab forge's listing, and `/attention remote` lists them as it does a GitHub repo's.
