**Why:** Two PRs that each add a board item conflict every time, and each conflict costs a hand rebase and a full re-precheck. `board_edit.py add` hands the write to ledgerboard's `plan_add()`, which inserts the new item above the first item of its section (`_under()`, `files/scripts/ledgerboard/board.py` ~220–235). So two concurrent adds always write the same line. GitHub's merge does not run the merge drivers named in `.gitattributes`, so the conflict cannot be settled there and someone has to rebase by hand. Each rebase moves the head, so the precheck runs again (TD-245 reuses a pass only on an identical tree, and a rebase onto a moved main does not give one).

ShiftLead counted more than six such rebases (its PR #3025 was rebased three times). It asked for this entry from its TD-1482 (ShiftLead's designer, 2026-11-07), which waits on it and names this id. Every consumer that runs `board_edit.py` from its pin pays the same cost.

cadence.md §3.4 already says what the resolution is: *a board conflict is resolved by taking both sides, unread*. But no tool does it. A session rebases, edits the conflict markers by hand, and has to get a result the `board` row will pass, which means one the writers could have written.

**Resolved:** 2026-11-07 (PR #178) — files/scripts/board_edit.py replay_text(); cadence.md §3.4; tests/test_board_replay.sh

**Done when:** `board_edit.py replay` re-applies a branch's own board writes onto the base branch's board and commits the result. A test covers two branches that each add an item under the same section, and an add plus a done on the same item, both settled by replay with no hand edit. The command is named in cadence.md where the board helpers are, with a `files/docs/cadence-changes.md` line.
