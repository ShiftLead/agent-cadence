## TD-250: In a pinned repo cadence_changes.py reads no changes: a bump's convention changes reach no starting or running session

**Priority:** medium
**Type:** debt

**Status:** Resolved 2026-11-07

**Location:** files/scripts/cadence_changes.py changes_path() ~111, origin_entries() ~122; launcher/words.py _source_clone; launcher/agent_cadence.py ensure_tree; files/docs/cadence.md §3.7 (2), §9.19, §7.9; files/docs/cadence-changes.md; ShiftLead docs/ledger/archive/TD-1025.md (dev-cadence's entry, the drafted design)

**Why:** In a repo that runs agent-cadence from a pin (cadence.md §9.19), `cadence_changes.py` reads no convention changes. So a bump's changes reach neither a session starting in it (`--hook`, the SessionStart hook of §3.7 (2)) nor a session already running (`--json`, which ShiftLead's home relays, §3.7 (3)). The only one who hears of a change is the reviewer of the bump PR, through its body. §3.7 makes `docs/cadence-changes.md` the way a convention change reaches sessions, and for every pinned consumer that way is silent.

The cause: `changes_path()` (`files/scripts/cadence_changes.py` ~111) returns the path beside the script only when the script lives inside the repo. Run from the pinned tree (the launcher's cache, outside the repo), it falls back to the consumer layout, `docs/cadence-changes.md`. A migrated repo has no such file, because `sync.sh --pin` removes the SYNC copies and `docs/cadence-changes.md` is one of them (`sync.sh` `SYNC_FILES`). So `origin_entries()` (~122) reads `origin/<default>:docs/cadence-changes.md`, gets nothing, and both modes say nothing, with no error.

Verified 2026-11-07 by the asker on agent-cadence main (`changes_path` / `origin_entries`), and in a pinned ledgerboard worktree, where `--list` prints *no cadence changes*. Checked again in the code while filing.

Asked by Paul on 2026-11-07, through his session `ao-led-tds-ledger`. It was drafted for him on 2026-10-26 as ShiftLead's TD-1025 *dev-cadence's entry*, and never filed.

**Resolved:** 2026-11-07 (PR #186)

**Done when:** In a pinned repo, `--json` and `--list` give the entries of origin's pin, with `landed` at the merge that brought each, and `--hook` prints an entry a bump brought, once per worktree. A synced copy and this repo keep their reading. cadence.md §3.7 (2), §9.19 and §7.9 say so, and offline fixture tests hold each case.
