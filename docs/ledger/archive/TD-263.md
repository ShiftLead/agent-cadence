**Why:** ledgerboard v3.0 is tagged (Paul's release, 2026-11-14; ShiftLead/ledgerboard Release PR #327, tag `v3.0`). This repo vendors v2.8 (`files/scripts/ledgerboard/`, TD-259), and ShiftLead's own vendor follows this one: ledgerboard's plans put agent-cadence first, then ShiftLead (TD-098's plan, D12 and *Consumers*). Until this lands, every v3.0 behaviour waits, in both repos.

v3.0 changes two things this repo meets:
- **The ledger's old forms are gone** (ledgerboard TD-078): `Waits`, `Taken by`, the old decision form and a header `Resolved` are retired errors, and `migrate` is removed. So the ledger must be clean *before* the vendor, with v2.8 still in hand. TD-078's plan D5 states the precondition: run with the last v2.x, `ledger.py migrate --plan --release 2.8` prints no entry holding `changes` or `stops`, and the vendor PR records that output before vendoring. On 2026-11-14 it showed two, TD-262 and the archived TD-260, each `Added comment → Log`; the PR that filed this entry migrated both.
- **The board becomes a directory of item files** (ledgerboard TD-070, its migration TD-098). `docs/user_attention.md` is split with `board.py split` in the same vendor PR, and every script here that reads the board as text or by line moves to the `Board` that `load_board()` gives. TD-098's plan, section *Consumers*, lists agent-cadence's lines one by one (`board_edit.py`, `check_cadence.py`'s board rows and carve-outs, `nudge_user_attention.py`, `list_sessions.py`, `gate_sweep.py`, `ledger.py`'s `BOARD_REL`, `tests/test_parity.sh`, and more), with the grep and the before/after reader runs that prove it.
